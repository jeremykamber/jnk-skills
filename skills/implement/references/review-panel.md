# The review panel — six skeptics on one diff

A reviewed slice gets six subagents, one question each, run in one batch over the same diff. Seat 1 hunts defects in the code as written. Seats 2–4 judge the design, each against a different group of Ousterhout's red flags and the moves that retire them; seat 5 asks the whole-diff question — did this change need all of these parts? Seat 6 is primed that the bugs are there and does not stop at the first. The shape is the point: one generalist reviewer reads the whole diff the same way and misses what a seat with a single question would have caught.

Used by: `jnk-3-implement` step 4 (a slice the route marked for review), `jnk-4-verify` step 5 (fresh eyes on a risky change), `jnk-oneshot` step 6 (a substantial or risky change).

## Running the panel

- **One seat per subagent, its brief quoted verbatim** — never this whole file. A seat that has read the other five is a generalist again, and each brief is written to be the only thing in its head.
- **The same context for every seat:** the diff under review (the slice's files, or the whole change), the tests the diff touches, the project's `AGENTS.md` — **the file itself, never a restatement of it** — the acceptance spec `features/*.feature` when one exists, and `depth --changed --base <ref> --json` for the changed files. That last one matters: `depth` decides nine of the fourteen red flags from the source text and lists them with their repair moves under `moves`, so no seat re-argues a decidable flag. The seats read for the flags a tool cannot decide — that is what a subagent is for.
- **All six in one batch, read-only.** The panel reads in parallel; **one writer repairs serially.** Six seats editing one tree race on the same files, and four quality seats editing one file produce four conflicting fixes — a review that damages the code is not a review. The panel's product is findings with a named move; the repair is the implementer's, applied one at a time, with the gates re-run after.
- **Every seat answers in the same shape:** `[seat] [high|med|low] location — the finding — why it matters — the move`. A seat with nothing to report says so plainly and says why (the tests cover X, the boundary is handled at Y). An all-clear with reasons is a valid result; a manufactured finding to look busy is a failed seat.
- **Moves are chosen, not invented.** For the nine flags `depth` decides, the menu is its own — `depth --explain <flag>` prints the ways to fix it and when each applies. For the flags no tool decides, the menu is in the seat brief. Prefer the smallest move that answers the finding.
- **Scale by seat, not by skipping review.** A reviewed slice runs all six. When the route names one risk ("the retry loop is the risk here"), say which seats you are not running and why — a narrower panel is a decision, never a default.

## The triage rule

Every finding gets one of three answers, out loud: **fixed** with the move the seat named, **squawked** with a reason, or **rejected as wrong** with a reason. A finding you neither fix nor answer is one you decided to keep, and saying so is the difference between a decision and an oversight. Findings that survive triage feed the layered walkthrough at the gate, one line each: what the skeptic found, how it resolved.

## Seat 1 — Correctness and craft

**Your question: is the code as written correct — the logic, the APIs it calls, and the code that no longer needs to exist?**

You are not reviewing the design; the other seats are. Read the code as if you were the one who would have to debug it at 3 a.m. Cite the line and the input or sequence that triggers the defect.

**Hunt these, the failure modes machine-written code actually produces:**

- **Plausible-but-wrong logic.** Code that reads correctly and is subtly wrong: an off-by-one; a boundary inclusive where it must be exclusive (`<=` for a `<`); the wrong variable or field from a copy-paste; an inverted comparison; a "simplification" that dropped a term; a default that hides a missing value; rounding applied at the wrong end.
- **API calls that are not correct.** The wrong function or overload; arguments in the wrong order; a return value ignored (an error, a count, an iterator); an async call not awaited, or awaited where the calls should run together; a mutation of an argument the caller still owns; a wrong or deprecated option; a type assertion (`as`, `!`, `any`) standing in for a check; a string parsed where the typed value was already in hand.
- **Dead code.** An unreachable branch; a guard for a state that cannot occur; code kept "just in case"; an export, parameter, field or import nothing reads; commented-out code; a test for behavior that no longer exists.
- **Silent fallbacks.** An exception caught, logged and defaulted; `??` or `||` masking a real missing value; a retry that hides the cause; a parse that returns an empty object on failure. The defect is not that it fails — it is that it fails where the caller cannot see it.
- **Tests that pass for the wrong reason.** An assertion that cannot fail; a mock that makes the test tautological; a fixture that drifted from the real shape; a test that still exercises the old path; `toBeDefined()` where the value mattered. If a test would still pass against the pre-change code, name it and say why.
- **Hidden behavior changes.** A rename, extraction or "cleanup" that changes evaluation order, error paths, side-effect count, or caching.
- **The edges nobody thought of.** Empty, one, many, zero, negative, NaN and Infinity, unicode, the second call, the concurrent call.
- **Model output left unenforced.** Where the diff touches an LLM call: output parsed or typed with no validation, or shipped with no judge pass against the stated rubric.

**Moves.** Delete the dead code. Fix the call or the signature it was written against. Make the failure loud at the first point it can happen. Make the test exercise the real path and assert the value. A guard that cannot be made to fail is not a guard — say so.

## Seat 2 — Knowledge and the interface: leakage, exposure, names, comments

**Your question: does this diff write one piece of knowledge in two places, publish more than a caller needs, or hide the abstraction behind a vague name or a narrating comment?**

*The philosophy.* Complexity has two causes — dependencies and obscurity — and both live at the interface. **Information leakage** is one design decision (a format, a field list, a magic value, an assumption about ordering) written in more than one place: the two copies are now coupled by something nobody wrote down, so a small change becomes edits in several modules — the change-amplification symptom, in its purest form. **Overexposure** is an interface that publishes more than its callers need — a helper exported, a field left mutable, a type that leaks the representation. Every published thing becomes a promise, and a promise you cannot take back is a constraint on every future change. **Comments** are how the abstraction is written down: a comment that repeats its line can be written by someone who understood nothing, so it carries no information; a declaration comment that narrates the implementation makes the reader learn mechanism the abstraction existed to hide. **Names** are the cheapest documentation there is. A vague name (`manager`, `handler`, `process`, `data`, `util`, `info`, `flag`, `do`, `sync`) forces every reader into the body; a thing that resists a precise name is usually two things wearing one hat.

**Hunt:** the same literal, regex, field list or shape written in two modules (`depth`'s `leaked-literal` and `leaked-shape`, already listed for you — read the ones the tool could not decide: an undocumented format shared by convention, a field order both sides assume, an id scheme reimplemented); an export nothing outside the module imports; a public method only the same class calls; a comment that is the line below it in other words; a declaration comment explaining how rather than what it promises; a name that could describe four different things; a subtlety only the author knows and no comment states.

**Moves.** Give the leaked knowledge one owner and make the other side ask for it. Raise the leaked literal to a named constant in the module that owns the decision; declare the shape once, where it is owned, and import it. Narrow the interface: make it private, delete the export, return a narrower type, take a narrower parameter. Delete the repeated comment, or raise it to intent — why, the constraint, the unit, whether an end is inclusive, what null means. Rename to the precise thing, or split the entity that resists a name. When the subtlety cannot be removed, state it at the interface the caller reads, not in the body.

## Seat 3 — Module shape: shallow, pass-through, conjoined, temporal

**Your question: is each element here deeper than the interface it imposes — or is the diff paying for structure that carries nothing?**

*The philosophy.* Depth is the functionality a module provides divided by the interface complexity it imposes on callers. A **shallow module** costs the reader the same interface as a deep one and returns almost nothing: a one-statement method, a class existing to hold a single method, an accessor that adds no meaning. Its cost is not lines — it is that every reader must open it to find nothing, and every caller has one more name to learn. The fix is usually not "make it shorter" but "remove the interface": **inline it into its caller** when the call site reads no worse than the body; **raise the interface** when several callers repeat a sequence it implements one step of; **merge it into the module that owns the data it touches** when it is a thin accessor over another module's state. Keep it only when the name marks a domain concept others will search for, or the seam is deliberate — and record that. A **pass-through method** forwards to a method of the same name: the interface grew and no knowledge moved; if the layer hides nothing, expose the lower object and delete the method (unless the lower interface leaks a representation the upper module is hiding). A **pass-through variable** is threaded down three or more levels and never read, only forwarded: every frame's signature carries a dependency none of them needs; put it on the object that owns the state, or make it module context. **Conjoined methods** are two things that look like one: every reader must understand both to change either, and every caller who wants one gets both. The test is whether you can understand one part without the other — if not, split at the seam. The honest inverse: if the two parts share most of their state, and a split would force that state to travel between them, the fix is merging, not splitting. **Temporal decomposition** organizes the code by the order things happen (read, then parse, then validate, then save — one module per step) rather than by the knowledge each step holds, so one piece of knowledge appears in several steps and a format change touches all of them. `depth`'s `co-change-without-import` is its fingerprint: two files that keep changing together with no dependency between them.

**Hunt:** `depth`'s decidable findings as your starting list (`shallow-method`, `pass-through`, `forwarded-parameter`, `co-change-without-import`), then the shape of what it cannot see — a service whose every method is a one-line delegate to a repository; a `getX` that returns a field after a check; an interface with one implementation that adds no invariant; a method whose name says two things.

**Moves.** Use `depth --explain <flag>` for every decidable finding — the moves there carry the conditions under which each applies and the cases where it does not. Conjoining: split at the seam, or merge when the parts cannot be told apart. Temporal: redraw the boundaries around the knowledge, keep the sequence in one orchestrator that holds no domain knowledge.

## Seat 4 — Generality and repetition: special/general mixture, duplication, the wrong abstraction

**Your question: is the generality in this diff earned by its callers — and is the duplication here one piece of knowledge, or two things that only look alike?**

*The philosophy.* A **somewhat general-purpose** module is deeper than one that serves exactly one case, because it hides more functionality behind the same interface — but generality is paid for by the use cases in hand, never by the ones hoped for. An abstraction with one caller is a guess, and guesses about the second caller are usually wrong. **Special/general mixture** is the failure where a special case lives inside a general mechanism: a change to the special case now risks the general one, and the general mechanism ships with the special case's quirks, so it can never be reused cleanly. **Repetition** is a finding when the copies encode one piece of knowledge — they will need to change together, and one of them will be missed; `depth`'s `leaked-literal` and `leaked-shape` are the mechanical detectors of exactly that. Repetition is *not* a finding when the similar-looking code serves different decisions: joining those creates a dependency between two things that merely resembled each other, and the next change has to fight the join. Duplication is far cheaper than the wrong abstraction. Wait for the third occurrence; extract only when the interface the extraction creates is simpler than what it replaces; and the moment an abstraction needs a new parameter or a conditional to serve a new caller, it has stopped being an abstraction — undo it.

**Hunt:** a "generic" helper with one caller and three options; a config knob with a single value in the tree; an abstraction whose only caller passes a flag to select behavior; a general mechanism carrying a special-purpose branch ("unless it's the import case…"); copies that must change together and don't (or ones that were joined and now need a parameter per caller); special-purpose code sitting in a general-purpose module (or the reverse); an extracted type added to the public surface for one internal use.

**Moves.** Split the special case out of the general mechanism, or move the general part down to where both callers can share it. For repetition: extract into one owner on the third occurrence, and only if the resulting interface is simpler than the duplication; otherwise keep the copies and name each one for its own decision. For an over-general abstraction: inline it back to its one caller, or delete the unused options. Say plainly when a piece of repetition is legitimate and why — that finding is closed, not deferred.

## Seat 5 — Simplification: the skeptical senior

**Your question: did this change need all of these parts?**

Read the diff as a skeptical senior developer whose first reaction is *"man, why is this junior dev making things so complicated?"* — then back the reaction with the code. This seat exists because "it works" and "it has no red flags" are both compatible with a design nobody can hold in their head.

*The philosophy.* Complexity is what the next engineer must know to make one change. Every module, layer, interface, option, cache, abstraction, config knob, and piece of state is something a person must learn and keep consistent with everything else — so the question here is not correctness (seat 1) and not the flags one by one (seats 2–4) but the whole diff: **could this behavior be produced with fewer things?** The simplest code is the code that no longer exists: it hosts no bug, needs no test, and drifts with nothing.

**Hunt:** a module with one implementation and one caller (is the interface earning its keep?); a function that only forwards; a helper used once; an option with a single value, or a config the code could decide; a cache with no measurement behind it; a retry with no known failure to survive; a defensive check on a value that cannot occur; a wrapper type that adds no invariant; a state field that could be derived; an interface wider than any caller uses; a three-line `utils` module; a `try`/`catch` whose only handling is log-and-continue where the caller could simply be told; concurrency added before a measurement; a comment standing in for a name; a name standing in for an explanation. Then **obscurity**: could a reader follow this without the comment, or without opening the callee? If not, make it obvious — rename to the intent, extract the intent as the function's name, reorder so the main path reads first, replace the clever expression with the boring one, and put the genuine surprise at the interface (a why-comment) instead of in the body.

**The fences — say these out loud, because simplification with no fence is destruction.**

- Required behavior and guarantees are not simplifiable. Error handling for a case that can happen, validation of data that can be bad, a seam the design needs at a boundary, a public interface something outside this change consumes — all stay. To remove one, argue the case it exists for; a hunch is not an argument.
- The wrong simplification costs exactly what the wrong abstraction costs (seat 4's rule): two similar lines serving different decisions do not get merged.
- Simpler means fewer things to know, not fewer lines. An extraction that names a concept simplifies; an inlining that makes the caller recite the callee does not.
- Deletions keep the tests green and the acceptance scenarios passing. Verify, do not assume.

**Output.** The diff's headline, concretely: `[5/simplification] high — src/plan/route.ts:88 — four concepts and a cache to compute one value — the reader pays for machinery that measured nothing — move: delete the cache, inline shapeOf, keep one function`. The strongest finding this seat can make is "delete this, and nothing else changes".

## Seat 6 — The bug hunter

**Your question: there are several issues and bugs in this code. Find them.**

The other seats judge what is in front of them. You assume the bugs are there and go where the tests do not look — the priming is deliberate: the recall-first stance finds what a confirmatory read misses. The discipline is in the output: **every finding names the trigger** (the input, the ordering, the state) **and the wrong behavior it produces.** A suspicion you cannot trigger is still worth naming — label it a suspicion — but you may not imply a bug you cannot describe.

**Where they live.** The branch the suite never takes: an error path, a partial-failure path, a fallback. The boundary the tests skipped: 0, 1, empty, max, max+1, negative, NaN, unicode, Feb 29, DST, midnight UTC. The second call: idempotence, reuse after close or dispose, a cached value gone stale, a queue drained twice. Ordering and concurrency: two calls in flight, an `await` missing, a shared mutable, a lock released twice, a promise nobody handles. The assumption about the caller: non-null, unique id, well-formed, sorted, non-empty, single-threaded. Resource lifetime: a file, socket, subscription, listener or timer not released on the failure path. Numbers and text: float rounding, integer division, locale-dependent parsing, a string cut mid-codepoint. The mutant the suite survives — if one exists, the assertion is missing. The call nobody expected to fail, so nobody handles it.

**Method.** For each behavior the diff changes, write down the input or sequence that would falsify it, then run it or trace it to the wrong result before reporting. The diff's own tests are the first place to look for what is uncovered: the paths they never enter are the paths to attack. When the change warrants the exhaustive version, that is `/skill:jnk-attack` — name it in your report rather than duplicating it.
